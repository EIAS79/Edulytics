# Edulytics — خطة V2 من الصفر: اختيار أفضل معمارية ثم الانتقال الآمن إلى Neon
**التاريخ:** 9 أكتوبر 2026  
**المستودع:** `EIAS79/Edulytics`  
**فرع العمل:** `feat/neon-clean-bootstrap-json-content-20261008`  
**الحالة:** وثيقة قرار وتنفيذ تدريجي، **ليست شهادة بإتمام النشر**. هذه النسخة تحل محل خطة V1 كمرجع للقرار، دون إلغاء الكود واختباراته الناجحة.

## 0. لماذا أعيدت الخطة؟
الهدف من نقاشنا كان اختيار أفضل حل، وليس فرض قاعدة «كل المناهج في Neon» أو «كل المناهج في JSON». كانت V1 قد بدأت بتصميم هجين ونفذت تخزين **النصوص التعليمية** في JSON مع إبقاء **5,110 هوية درس** وإطار المناهج والعلاقات في PostgreSQL. أثبت اختبار PostgreSQL 18 إمكانية إعادة البناء دون أي مستخدم أو مدرسة ودون صفوف شروحات في قاعدة البيانات؛ لكنه **لم يثبت بعد أن هذا هو أقل تصميم استهلاكًا أو الأسرع**. لذلك تبدأ V2 بقرار معماري مبني على الكود والقياسات.

## 1. الشروط التي لا تتغير
- **لا ننقل** أي حسابات أو مدارس أو طلاب أو مدرسين أو مشرفين أو مدراء أو نتائج أو محاولات أو فواتير أو رسائل تشغيل أو بيانات تجريبية من Neon القديم.
- لا نقرأ أو نغيّر أو نحذف مشروع Neon القديم؛ ولا ندفع لإعادة فتح حصته أو ننتظر تجديدها.
- GitHub هو **مصدر الحقيقة لمحتوى المناهج العام المعتمد**؛ لا نخلط بين محتوى المنصة العام وما يضيفه المستخدمون أو المدارس مستقبلًا.
- لا نعطّل Practice وAdaptive Practice والتقييمات والنتائج والصلاحيات والعزل بين المدارس والاشتراكات.
- لا نختلق مخرجات تعلم رسمية أو شروحات ناقصة للحصول على نتيجة تدقيق خضراء.
- لا نغيّر `main` أو Render الإنتاجي قبل اجتياز بوابات الاختبار وتحديد Neon الجديد بدقة.
- نقيس **عدد استعلامات PostgreSQL، حجم الصفوف المنقولة، زمن الاستجابة، واستهلاك egress الفعلي**؛ تقليل حجم قاعدة البيانات وحده لا يعني تقليل الشبكة.

## 2. الخيارات الثلاثة المطلوب تقييمها

| الخيار | المحتوى التعليمي العام | PostgreSQL | الفائدة | الخطر / الملاحظة |
|---|---|---|---|---|
| A: Database-centric | النصوص والهياكل في PostgreSQL | جميع الجداول والروابط | تغييرات بسيطة نسبيًا | أحمال قراءة ونصوص أكبر ما لم نستخدم Cache |
| B: JSON-centric | جميع المناهج والوحدات والهويات والمخرجات والروابط في JSON مع فهرس RAM | بيانات المستخدمين والتشغيل فقط + مفاتيح نصية ثابتة عند الحاجة | تخفيض كبير محتمل في طلبات المحتوى الثابت | يتطلب إعادة تصميم علاقات EF Core والمفاتيح الأجنبية، وتعديل Practice/Assessment |
| C: Hybrid minimal + cache | المصدر العام كله في JSON، والشرح التفصيلي يُخدم من JSON/الذاكرة | **أقل سجلات مرجعية لازمة** للهويات والعلاقات وبيانات المدارس/المستخدمين | توازن محتمل بين استعلامات قليلة والتوافق المرجعي | يتطلب فهرس RAM منضبطًا واختبار عدم قدم البيانات |

**الاختيار الحالي مؤقت، وليس حكمًا قبل القياس.** يمكن أن يكون C هو الأفضل إذا أثبتت الاختبارات أن إزالة بقية الجداول تكسر سلامة العلاقات أو تزيد التعقيد دون مكسب حقيقي. ويجوز نقل مزيد من قراءات المرجع إلى RAM دون حذف مفاتيحه من PostgreSQL.

### دليل من الكود الحالي
- `SchoolCurriculumAdoption.FrameworkVersionId` يربط اختيار مدرسة بإصدار منهج.
- `CurriculumPedagogicalLessonOutcome` يربط هوية الدرس بمخرج رسمي.
- `LessonContentRepository.ListCanonicalContentsAsync` يقرأ بيانات المرجع من Neon حتى عند اختيار قراءة شرح JSON.
- `LessonContentService` يفحص دور الطالب/الموظف وتبنّي المدرسة للمنهج قبل إظهار الدرس، وهذا يجب أن يبقى.
- مخطط المناهج العام مصدره `*.curriculum-pack.json`؛ الشروحات مصدرها `*.lesson-content-pack.json`؛ والبنية التعليمية مصدرها `*.lesson-blueprint.json`.

## 3. مقياس القرار المعماري
يُمنع الإعلان عن «الخيار الأفضل» إلا بعد مقارنة A/B/C على نفس بيانات الاختبار وبنفس السيناريوهات؛ وتشمل:
1. **الصحة والأمان (شرط نجاح إلزامي):** تطابق قائمة الدروس، تراخيص النشر، العزل المدرسي، الروابط بمخرجات التعلم، محاولات Practice، التقييمات والترجمات.
2. **استعلامات DB:** لكل صفحة (قائمة المناهج، قائمة الدروس، تفاصيل الدرس، Practice، التقارير): عدد الأوامر ووقت قواعد البيانات والبيانات المنقولة.
3. **زمن الاستجابة:** p50/p95 مع عملية باردة وبعد تسخين Cache، ومستخدم واحد وعدة مستخدمين.
4. **الذاكرة والنشر:** حجم JSON المحمّل للذاكرة، زمن تهيئته، وتطابق الإصدارات عند إعادة النشر.
5. **التكلفة:** egress/CU-hours المقاسة في بيئة تجريبية، لا أرقام تخمينية بالدولار.
6. **قابلية الصيانة:** عدد العلاقات والمكونات التي تحتاج إعادة كتابة، ومخاطر العودة للخلف.

**قاعدة الاختيار:** أي خيار يخرق الصحة أو الصلاحيات أو العلاقات اللازمة يُرفض مهما كان موفرًا. بعد استبعاد المخالفين، نختار الأقل في الاستعلامات/egress الفعلي والتعقيد، مع هامش أمان للحصة المجانية. عند عدم توفر قياس Neon الفعلي، القرار يظل «مؤقتًا» حتى مرحلة التشغيل.

## 4. المراحل الاثنتا عشرة المعدلة

### المرحلة 1 — تثبيت الحالة الفعلية وخريطة الاعتماديات
حصر النسخة/الفرع/PR، من يقرأ كل جدول، ومسارات JSON/EF/Practice/Analytics والصلاحيات، وتسجيل اختبارات CI السابقة.  
**قبول:** خريطة كاملة للمخاطر والروابط وحالة ملفات المحتوى. **الحالة:** مراجعة أولية اكتملت، ويُستكمل تحليل الاستعلامات.

### المرحلة 2 — نماذج الخيارات وقياسات المقارنة
بناء اختبارات منفصلة A/B/C أو محاكاة مفصلة للقراءة فقط، وإضافة SQL command count وحجم النتائج وتوقيت p95 بالسيناريوهات نفسها؛ دون توجيه طلب واحد لـNeon القديم.  
**قبول:** جدول مقارن قابل لإعادة التشغيل يبيّن الأرقام والانحرافات. **الحالة:** بدء التنفيذ؛ قياس الـJSON/DB الجاري إعداده.

### المرحلة 3 — قرار ADR النهائي
تسجيل ما يبقى في PostgreSQL بالاسم وما يبقى في JSON، وسبب كل استثناء من منظور FK/التوافق/الزمن/الحصة.  
**قبول:** قرار موثق مدعوم بالأرقام، وليس بافتراضات.

### المرحلة 4 — تدقيق محتوى GitHub
فحص المناهج الأربعة و69 حزمة محتوى و50 مخططًا وملفي RichV2، والتحقق من الهوية والترجمة والمصدر والرياضيات والعلاقات والنشر.  
**قبول:** جرد واضح للدروس المعتمدة **وليس مجرد عدد المدخلات**. **النتيجة الحالية:** 5,110 كود درس فريد، لكن فحص التغطية الصارم = 62/64؛ ينقص UAE الصف الخامس والسادس Advanced. لا نغيّر علامة الفشل لإخفائه.

### المرحلة 5 — محرك قراءة موحد من JSON وRAM
فهرس إصدار/بصمة/لغة للمحتوى العام؛ مصادقة وصلاحيات تبقى في الخدمات، ولا يتحول JSON إلى endpoint عام يتجاوز الصلاحيات. قواعد منع المحتوى القديم وحدود Cache.  
**قبول:** استجابة وحقوق وصول متطابقة مع API الحالي.

### المرحلة 6 — تقليص مرجع PostgreSQL بالقدر الآمن
حصر الجداول المرجعية اللازمة لـFK والتقييمات والتبنّي المدرسي، ومنع استعلامات المحتوى الثابت المكررة. أي حذف جدول مرجعي يحتاج Migration واختبارات اعتماديات مستقلة؛ لا نحذف لأن الاسم «تعليمي» فقط.  
**قبول:** استهلاك أقل، بلا FK مكسور.

### المرحلة 7 — إصلاح قراءة قواعد البيانات والعمال
ضم إصلاح IdlePollBackoff (PR #418) داخل فرع الاختبار، تقليل الاستعلامات والقراءات الكبيرة، منع إعادة استيراد المناهج عند كل تشغيل، وضبط الاستعلامات والفهارس.  
**قبول:** اختبارات سلامة Outbox/Analytics، وقياسات idle/database commands.

### المرحلة 8 — قاعدة مؤقتة نظيفة واختبارات شاملة
PostgreSQL 18 + EF migrations + تحميل من المصدر فقط، ولا حسابات قديمة أو Demo. اختبار الطالب والمدرس، Practice، التقييمات، الحسابات الجديدة الاصطناعية، الصلاحيات واللغة.  
**قبول:** CI شامل + نتائج SQL قابلة لإعادة الإنتاج، وبدون بيانات أشخاص حقيقية.

### المرحلة 9 — تجهيز حساب Neon الجديد
تحديد الحساب/الـproject والفرع والقاعدة المقصودة، إنشاء قاعدة مستقلة ضمن حدود الخطة، كلمة المرور في أسرار الاستضافة، اتصال pooled للتطبيق وdirect للترحيلات، ثم تنفيذ migrations والتهيئة.  
**قبول:** تأكيد الصفر لبيانات المستخدمين والمدارس، وتطابق عدد الروابط والمناهج. **غير منفذ** إلى أن يتوفر اتصال الحساب الجديد.

### المرحلة 10 — نشر Render الآمن
الخدمة المستهدفة `Edulytics` (`srv-dakq5n2fngtc73a62i10`) وليس `Edulytics Public` الثابتة. ربط Neon الجديد فقط بعد اكتمال الاختبارات وخطة العودة، وتأكيد عدم وجود حسابات أو مدارس تجريبية.  
**قبول:** smoke tests وتوجيه صحيح ونقطة رجوع.

### المرحلة 11 — قياس الاستهلاك والإصلاح النهائي
مراقبة الـegress الحقيقي وحجم البيانات وعدد SQL وCU-hours خلال idle والتحميل الفعلي، وتحسين Cache إذا أظهرت القياسات حاجة.  
**قبول:** استهلاك آمن موثق مقابل حدود الخطة، وأخطاء منخفضة.

### المرحلة 12 — اعتماد الإنتاج والتسليم
تقرير قرار التصميم مع أسباب فوزه، وسجلات CI، وحصر الدروس الجاهزة، وبيانات الـNeon/Render المقصودة دون أسرار، ووثيقة رجوع وإعادة بناء.  
**قبول:** تحقق فعلي من كل الشروط؛ لا تُعلن المراحل مكتملة بلا دليل.

## 5. الإنجاز الفعلي الذي لا نعيد كتابته بلا داعٍ
- PR #419 فرع التنفيذ؛ `main` لم يتغير.
- اختبار PostgreSQL 18 السابق أعاد إنشاء **4 أطر و5,110 هوية درس، مع 0 مستخدم و0 مدارس و0 صفوف نصوص**؛ الرابط: https://github.com/EIAS79/Edulytics/actions/runs/37847439326
- جرد JSON: 5,110 هوية فريدة بدون تكرار بنيوي وفق المدقق الحالي.
- اختبارات .NET شاملة سابقة: **2,201 اختبارًا ناجحًا**، لكن بوابة اكتمال مناهج Phase29 ما زالت حمراء لمسارين.
- إصلاح Backoff من PR #418 تم إدراجه في فرع الانتقال للاختبار، وليس في `main`.
- لا Neon قديم، لا Render production cutover، لا حسابات قديمة.

## 6. التنفيذ الذي يبدأ مع V2
1. إضافة مقارنة ومعيار قياس قابل لإعادة التشغيل لقراءة محتوى JSON.
2. تقليل عدد أوامر SQL في مسار قراءة الدرس الواحد دون تغيير التحقق من الصلاحية.
3. تفعيل اختبار PostgreSQL 18 لعدد أوامر SQL ومنع جلب جداول الشروحات من Neon.
4. تحديث PR #419 وإبقاءه Draft حتى اجتياز بوابات الأمان والمناهج والتشغيل.
5. بعد ذلك نقرر هل الفهرسة الكاملة للمنهج في RAM تستحق إزالة بعض قراءاته من PostgreSQL مع الاحتفاظ بعلاقات FK اللازمة.

## 7. ما لا نستطيع ادعاءه حاليًا
- لا يوجد بعد دليل بأن التخزين الكامل في JSON أحسن من التصميم الهجين على الأحمال الحقيقية.
- لا توجد قياسات egress فعلية من Neon الجديد ولا نجاح لنشر Render عليه.
- نجاح استيراد 5,110 هوية لا يثبت اكتمال جميع محتويات 64 مسارًا أو صحتها التعليمية.
- الخطة ليست إذنًا لتعديل Neon القديم أو حذف أي بيانات.
