## 1. المهمة والنجاح المطلوب

نريد آلية عملية لمراجعة **500/500 درس في نطاق واحد**، وتصحيح كل مشكلة مشتركة مرة واحدة حيث يثبت اشتراك السبب، والتحقق من جميع الدروس، ثم إصدار **قرار اعتماد جماعي واحد** — مع الاحتفاظ بهوية كل درس وأهدافه وأدلته.

**الفكرتان الأساسيتان من صاحب المشروع:**

1. **Academic Source Memory / Read Once:** قراءة الكتب الأصلية قراءة تأسيسية، واستخراج الأهداف والمعايير والتسلسل والرياضيات والأمثلة والرسومات والأنشطة والأسئلة والإجابات ومتطلبات المطابقة، وحفظ الناتج موثقًا ومتاحًا للاسترجاع. بعد قفل المصدر لا تعود المراجعة الروتينية إلى الكتب.
2. **Universal Bulk Audit & Root-Cause Repair:** فحص المنهج بصورة جماعية، واكتشاف العيوب المتشابهة في الرياضيات **بكل عائلاتها**، والشرح والأنشطة والتقييم والعرض، وإصلاح المكون أو النمط المشترك مرة واحدة مع التحقق من جميع المواضع المتأثرة.

**إضافتان ملزمتان من النقاش:**

- **Full-Batch Processing:** كل تشغيل دفعة له Manifest واحد يضم الـ500، ولا يُجزأ إلى دفعات تشغيل ثابتة من 50 أو 100، ولا Pilot مستقل قبل B01. المعالجة الداخلية يمكن أن تتوازى؛ المخرجات والاعتماد تغطي **500/500**.
- **Overlap Without Premature Certification:** تبدأ الفحوص والإصلاحات المستقلة مبكرًا أثناء وصول النتائج، بدل انتظار نهاية كل مرحلة؛ لكن نتيجة التحليل النهائي والاعتماد النهائي لا تصدران قبل تغطية الـ500 والتحقق على إصدار ثابت.

**الشرط الحاكم للانتقال:** بعد أن تصبح B01 معتمدة **ومنشورة على Render Live ومتحققًا من عملها فعليًا** فقط، تُفتح B02 للفحص والإصلاح؛ وتتكرر القاعدة إلى B04. تجهيز الفهرس العالمي للمنهج مسبقًا لا يُعد بدء فحص أي دفعة لاحقة.

**القاعدة الحاسمة:** «500/500» تعني *تغطية شاملة قابلة للإثبات*، لا أن كل ملف يجب تعديله أو أن كل خطوة يجب تشغيلها 500 مرة منفصلة أو أن ننتظر انتهاء كل خطوة لإطلاق عمل آخر مستقل.

### 2.2.1 سياسة أصالة أمثلة Edulytics والتشابه الطبيعي — قرار ملزم (2026-10-14)

1. **ملكية التأليف المستقل:** الشروحات والأمثلة والمسائل والأسئلة والأنشطة والرسومات التي أنشأها فريق Edulytics بصورة مستقلة هي محتوى Edulytics، حتى عندما تتشابه في الفكرة أو القيم العددية أو الخطوات الرياضية أو الهدف التعليمي مع مثال منشور في كتاب آخر. المقارنة مع مصدر موثوق للتحقق من الدقة والتوافق ليست في ذاتها نقلًا للمادة المحمية ولا تجعل ناشر المرجع مالكًا لتأليف Edulytics.
2. **التشابه وحده لا يثبت النسخ:** تتكرر في الرياضيات الأعداد والعمليات وطرق الحل والمصطلحات والتمثيلات القياسية، وبالتالي لا تتحول مطابقة مثال أو تسلسل حسابي أو هدف CCSS إلى `CONFIRMED_DEFECT` أو `BLOCKED_RIGHTS` تلقائيًا. كما لا يجوز استنتاج وقوع نسخ من نتائج فحص الكلمات أو `original-authorship-screen` وحدها.
3. **لا إعادة كتابة شكلية:** يحظر تغيير مثال رياضي صحيح أو حل مستقل أو نشاط مناسب **لمجرد أنه مشابه للمصدر**. يُسمح بالتعديل إذا كشف التحقق المستقل خطأً فعليًا في الرياضيات أو الهدف أو التدرج أو جودة العرض أو إذا ثبت نقل تعبير إبداعي محمي دون أساس استخدام صالح. يجب توثيق السبب الحقيقي للإصلاح ونطاقه ونتيجته.
4. **فصل مرجع التحقق عن مادة النشر:** الكتب الرسمية/الموثوقة تُستخدم كمرجع داخلي لمراجعة صحة المحتوى والأهداف والمهارات والأمثلة والتمثيلات. لا يُشترط إذن خاص من ناشر المرجع ولا إظهار اسمه للمستخدم لمجرد هذه المراجعة، عندما لا تنشر Edulytics تعبيرًا محميًا مأخوذًا منه. تظل روابط المصادر والبصمات وأدلة المطابقة داخل السجلات الأكاديمية.
5. **لا حصانة تلقائية بالتسمية:** التأليف المستقل يجب أن يكون حقيقيًا. إذا أثبتت مقارنة محددة نسخ أو ترجمة/اقتباس/تكييف نص أو رسم محمي، تُعالج حقوق ذلك العنصر بحسب ترخيصه الفعلي أو يُستبدل بمحتوى مستقل، **وليس** لمجرد وجود تشابه في مسألة رياضية. عدم كفاية الأدلة في مسألة جوهرية يُسجل للمراجعة دون `PASS` مصطنع أو اتهام بالنسخ.
6. **قاعدة تنفيذ وفحص:** عند اقتراح تعديل بسبب التشابه، يُطلب دليل إيجابي يتضمن `LessonCode`، موضع التعبير المقارن، توصيف العنصر المحمي إن وجد، وسبب اعتبار الحالة نقلًا غير مستقل، مع قرار `NO_ACTION_INDEPENDENT_OR_GENERIC` أو `CONFIRMED_COPYING_REQUIRES_ACTION` أو `REVIEW_UNRESOLVED`. قرارات الحقوق **لا** تحل محل L1–L6 أو الأبعاد الثمانية، ولا تعني اعتماد الدرس أو الدفعة.

## 4. البناء الأكاديمي العالمي — Read Once, Capture Completely

### 4.1 جرد موحد لجميع الدروس

نقرأ ونستكمل Inventory موثقًا للـ1,560، ونعيد استخدام الموجود الموثق قبل إنشاء الجديد: `LessonCode`، الصف، الوحدة، ترتيب الدرس، المصدر والطبعة، معيار CCSS، الصفحات، روابط كتاب الطالب/المعلم، حالة التغطية، والعلاقات/المهارات المعروفة. يكشف التكرارات والدروس المفقودة وعدم تطابق المصادر، ولا يفترض أن وجود عنوان يكفي لاكتمال الدرس.

### 4.2 بطاقة المصدر الأكاديمية

من **المرور التأسيسي المطلوب بعد استبعاد العناصر المثبتة سلفًا** نحفظ لكل درس ما يلزمه فعلًا:

- **Required:** الهوية، المصدر/الطبعة/الصفحات، CCSS، الأهداف الرئيسية والفرعية، المفاهيم الأساسية، هدف التقييم، دور المهارة، قيود ومجالات الرياضيات، معرفات الدليل.
- **Conditional:** الأمثلة التفصيلية والحلول، الخطوات، الرسومات/التمثيلات المنظمة، الأنشطة، الأخطاء التعليمية المقصودة، وحدات القياس، متطلبات البرهان، عائلات الأسئلة، الصيغ البديلة، متطلبات الواجهة؛ حسب طبيعة المصدر والدرس.
- **Optional:** إثراءات غير لازمة لتحقيق الهدف الأكاديمي المثبت.

كل حقل يُحفظ بحالة واحدة: `VERIFIED`، `NOT_APPLICABLE`، `NOT_IN_SOURCE`، أو `UNRESOLVED` مع سبب ورابط موضع المصدر. لا يصح مساواة حقل غير موجود في المصدر بحقل لم نقرأه.

**Source element manifest** لكل درس: قائمة الأهداف والأمثلة والأنشطة والرسومات والأسئلة المطلوب التقاطها، مع مصدر كل عنصر وحالة معالجته. الهدف كشف السهو أثناء القراءة، لا الاكتفاء بوجود JSON صحيح البنية.

### 4.3 تحقق وقفل المرجع قبل المقارنة

يمر المصدر في معالجة متصلة: `Locate → Read → Extract → Cross-check → Seal`.

يشترط `SOURCE_SEALED`:

1. إثبات هوية كل نسخة وصفحاتها، وعدم فقد عناصر المصدر اللازمة.
2. ربط كل هدف ومفهوم ومثال/نشاط/تمثيل مطلوب بموضعه.
3. تحقيق صحة البيانات الرياضية التي يمكن التحقق منها بصورة مستقلة؛ وفحص الرسومات والأصول اللازمة بما يتجاوز مجرد وجود روابط صور.
4. حسم أي `UNRESOLVED` مؤثر في المقارنة؛ عدم إلزام الدروس بتمثيلات غير موجودة أو غير لازمة لها.
5. بصمة سجل المرجع ونسخة Schema وإصدار المصدر وأثر التحقق.

**الرجوع للكتاب بعد القفل ليس خطوة اعتيادية.** إذا ثبت لاحقًا خطأ في الذاكرة، يُصحح بإجراء استثنائي، مع إبطال الأدلة المتأثرة فقط. لا يوجد ضمان مطلق بعدم اكتشاف خطأ في أي عملية استخراج بشرية أو آلية.

### 4.4 ما الفرق بين المطابقة والنسخ؟

المرجع لا يُستخدم لفرض نص أو صورة الكتاب حرفيًا. معيار النجاح هو **صحة CCSS والهدف والمفاهيم والمهارة والتمثيل أو النشاط المكافئ تربويًا**. إذا كان خط الأعداد نفسه مهارة الدرس، فلا يجوز حذفه بحجة وجود إجابة عددية صحيحة. إذا كان نوع الأداة غير جوهري، يمكن قبول بديل صحيح تعليميًا. تُوثق المبررات عند الاختلاف غير الحرفي.

### 4.5 متى نبدأ B01؟

- وجود **500 سجل مرجعي صالح** للدفعة (مقفل سابقًا أو استُكمل وأُقفل الآن) شرط لإغلاق المقارنة الجماعية وإصدار نتيجتها 500/500.
- يسمح بفحص العناصر التي اكتمل مرجعها وبالإصلاحات المشتركة المؤكدة أثناء استمرار تجهيز بقية سجلات B01؛ لا تُصدر بوابات إغلاق جماعية قبل اكتمال جميع سجلاتها.
- فهرس الـ1,560 عالمي من البداية؛ استكمال تفاصيل B02–B04 لا يفتح فحصها أو اعتمادها قبل وقتها، ولا يحجب تقدم B01 غير المتأثر.

## 5. الفهم الرياضي الشامل والسياق

### 5.1 فصل أربع هويات

لكل درس نحتفظ بـ: `Primary/Secondary Skills`، `Prerequisites`، `Mathematical Elements`، `Element Pedagogical Role`، `Shared Components`، `Required Verification Capabilities`.

مثال: درس قياس يستخدم `1/2` متر. المهارة التعليمية هي القياس؛ الكسر عنصر رياضي؛ عطل رسم الكسر يصلحه Renderer؛ ملاءمة التقييم تحددها أهداف القياس. المعادلة الخاطئة المعروضة لتعليم خطأ شائع لا تصحح آليًا كما لو كانت حلًا نموذجيًا.

### 5.2 فهرس عالمي للعناصر والقدرات

يشمل **ما يظهر فعلًا بالمناهج ومصادرها**: الأعداد والعمليات وقواعدها؛ الكسور والعشري والنسب والتناسب والنسب المئوية؛ الأسس الصحيحة والسالبة والكسرية؛ الجذور التربيعية والتكعيبية والنونية؛ التعابير وكثيرات الحدود؛ المعادلات والمتباينات والأنظمة؛ الدوال والعلاقات والمنحنيات؛ الهندسة والتحويلات والقياس والأبعاد والوحدات؛ الإحصاء والاحتمالات؛ المسائل الكلامية والنمذجة والتمثيلات البصرية؛ وأي نوع آخر تثبته المصادر.

- استخدام AST/Math IR typed حيث يلزم لإثبات المجالات والقيود والتحويلات والتكافؤ — لا مجرد استبدال نصي.
- **Track A:** العقد الأكاديمي يحدد *ما المطلوب تعليمه وفحصه*. **Track B:** النواة الرياضية تحدد *كيف يتم الحل والتحقق والتصحيح والتوليد*.
- لكل قدرة `SUPPORTED_AND_TESTED` أو `PARTIAL` أو `UNSUPPORTED`. لا `PASS` لقدرة غير مثبتة.
- أمثلة حرجة: `sqrt(x²)=|x|` على الأعداد الحقيقية؛ الجذور الزوجية والفردية تختلف في مجال السوالب؛ الأس السالب يتطلب مراعاة الصفر؛ التحقق من الوحدات والتقريب؛ الإجابات الرياضية المكافئة؛ البراهين/الأشكال وقيود السؤال.

### 5.3 مبدأ عدم بناء محركات عملاقة

يوجد Registry عالمي بالأنواع والمتطلبات، بينما تُنفذ قدرات Solver/Verifier/Renderer اللازمة للدفعة الجارية وتُثبت باختباراتها. لا نبني حلّالًا لكل الرياضيات المتقدمة قبل B01 ولا مولّدًا مستقلًا لكل درس.

## 6. محرك التشغيل: Full-Batch 500 + Overlapping Work

### 6.1 عقد تشغيل الدفعة

يُنشأ `Batch Manifest` واحد ثابت للـ500، له بصمة وهوية إصدار. جميع أدوات الفحص تقبل الـManifest الكامل وتعيد تغطية واحدة لـ**500 LessonCode فريدًا** بلا نقص أو تكرار.

**محظور** تقسيمه إداريًا أو أكاديميًا إلى دفعات مستقلة من 50/100 أو اعتماد جزئي. **مسموح** توزيع الحسابات داخليًا على Workers/Jobs وفق عمليات مستقلة (رياضيات، صور، أسئلة، اختبار واجهة، تحليل مصدر) ثم تجميع النتائج في المصفوفة الجماعية نفسها.

### 6.2 التداخل الزمني دون تأخير

تعمل أربعة مسارات متداخلة داخل B01:

1. **Source / Academic Comparison**: قراءة المرجع الجاهز ومقارنته بالمحتوى الفعلي.
2. **Global Math & Defect Analysis**: تحليل كل نتائج المقارنة المتاحة، وتصنيف سبب العيب، وربط العناصر والمكونات عبر الدفعة.
3. **Root-Cause Repair**: بدء إصلاح عيوب مشتركة **مؤكدة** بمجرد توافر الأدلة والتبعيات؛ لا حاجة لانتظار تحليل آخر درس لمشكلة مستقلة.
4. **Targeted Verification & Evidence**: اختبار أثر الإصلاحات وتخزين الأدلة الصحيحة مبكرًا.

**بوابات إغلاق فقط:**

- `COMPARISON_COMPLETE` عندما تسجل نتيجة لكل الـ500، ولا تعني نجاحها بالضرورة.
- `GLOBAL_ANALYSIS_COMPLETE` عندما يشمل التحليل **500/500** ويُحسم تجميع الأسباب الجذرية للدفعة أو تُصنف عوائقه صراحة.
- `FINAL_VERIFIED` عندما يثبت تحقق جميع متطلبات الـ500 على إصدار مستقر مع تجميع/إعادة تحقق الأدلة اللازمة.
- `BATCH_CERTIFIED` بعد جميع بوابات الاعتماد والسياسة القانونية والأمان وCI.

بذلك **نلغي حاجز الانتظار بين المراحل التنفيذية**، مع الحفاظ على الحاجز النهائي للتغطية والاعتماد.

### 6.3 التحكم في تزامن الإصلاحات

- القراءة والتحليل والاختبارات المستقلة يمكنها العمل بالتوازي.
- تغييرات المكوّن الواحد أو نفس ملفات المحتوى تُنسّق بواسطة مالك كتابة واحد ونسخة إصلاح واحدة، لتجنب تضارب Git والمخرجات.
- كل Repair Task يحدد `rootCauseId` و`affectedLessonCodes` و`affectedComponents` و`before/after` وقاعدة التحقق.
- إذا ظهر سبب جديد بعد إصلاح مبكر، قد يلزم تعديل آخر؛ لذلك **الاعتماد لا يتم على نتائج مرحلة متحركة** بل على نسخة مرشحة مجمدة.

### 6.4 لا تؤخر المهام لإكمال حزمة وهمية

تُنفذ المهمة المشتركة عندما تتوافر أدلتها ومدخلاتها. لا انتظار للوصول إلى 50 عنصرًا ولا دمج عيوب مختلفة تحت «مهارة واحدة». التجميع للتنفيذ يتم وفق المكوّن/العملية المشتركة، والتجميع للإصلاح وفق السبب الجذري المثبت.

## 10. Verification & Evidence — تحقق نهائي 500/500 مع Reuse آمن

### 10.1 التحقق أثناء الإصلاح وعند الإغلاق

- أثناء الإصلاحات: اختبارات محددة فقط للتبعيات التي تغيرت، مع حفظ الأدلة الصالحة التي لم تتأثر.
- بعد استقرار التغييرات: تجميد `Release Candidate SHA`، ثم تغطية كاملة للـ500 بأدلة صحيحة مع تشغيل اختبارات GitHub Actions/CI والتكامل وRich V2/Practice/الأمن اللازمة للمرشح **كله** مرة على كل مرشح نهائي مستقر.
- عند فشل الإغلاق، يُصلح السبب، وتُبطل الأدلة المتأثرة وتُعاد اختبارات النطاق المتأثر والبوابات الشاملة التي تغيرت صلاحيتها؛ لا إعادة تصفير الـ500 تلقائيًا.
- يختبر مسار طالب حقيقي على بيئة مصرح بها: `Open Lesson → Render → Start Practice → Answer → Grade → Feedback → Save Progress`، مع التحقق من الأدوار والعزل وعدم ادعاء تجربة يدوية لم تُنفذ.

### 10.2 أنواع الأدلة

- **Component Evidence:** رياضيات أو Renderer أو Generator أو Evaluator ضمن مدخلاته وإصداره، لا يثبت الهدف التعليمي وحده.
- **Lesson Evidence:** دليل خاص بهدف ومحتوى ومتطلبات كل `LessonCode`.
- **Runtime Evidence:** دليل عمل العرض والتفاعل والتصحيح والتخزين والصلاحيات في التطبيق الفعلي.

### 10.3 بصمات الأدلة ومصفوفة الاعتماديات

لكل دليل نخزن `evidenceId`, `LessonCode/coverageSet`, `requirementId`, `sourceSha256`, `sourceSemanticSha256`, `effectiveContentSha256`, `candidateSha`, `codeSha`, نسخ `SkillContract/QuestionFamily/Solver/Renderer/Rubric` عند الصلة، `testVersion`, `environmentFingerprint`, `runId`, `timestamp`, `result`, `coverageScope`. يعاد استخدامه فقط حين يثبت أن جميع التبعيات المؤثرة باقية ومتطابقة. لا تحديث صوري لبصمة دليل قديم.

**مصفوفة إبطال أدلة V4.3 الحاكمة (منقولة دون حذف لشروط التأثر):**

| نوع التغيير | نطاق إعادة التحقق أثناء الإصلاح |

| مصدر/طبعة/معيار/هدف درس | L1؛ ثم L2/L3/L4/L5 عند تأثر المطابقة؛ L6 إن تغير ما يُعرض |

إذا تعذّر إثبات حدود التأثر، **نوسّع** إعادة الاختبارات اللازمة ولا نستخدم Cache بلا سند.

مصفوفة واحدة لنطاق الدفعة، **500 صفًا** (أو 60) تربط كل متطلب بكل دليل صالح. الحالات `MISSING/PARTIAL/VALID/INVALIDATED/FAILED/BLOCKED`. نجاح اختبار عرض الكسور، مثلًا، لا يثبت تلقائيًا مطابقة أهداف كل درس يحتوي على كسر.

### 11.3 قواعد إثبات نتائج هذه البوابات

1. لا `PASS` إلا بدليل حقيقي قابل للتتبع، و`SHA` المحتوى الفعلي الذي يصل للطالب، وتاريخ/نطاق اختباره، ومعايير حقوق الاستخدام المطلوبة.
2. **لا L7 ولا human sign-off** ولا شهادات فردية متسلسلة؛ يحتفظ النظام بصف Evidence لكل درس، لكن يصدر **قرار واحد للدفعة**.
3. لا `BATCH_CERTIFIED` إذا كان أي درس ضمن 500/500 لديه فشل أو نقص أو دليل مبطل أو حقوق غير مثبتة أو اختبار L6 لم ينفذ في نطاقه.
4. الربط `Dimension → Gate → Requirement → Evidence` يمنع إسقاط شرط أو احتساب الاختبار نفسه لتغطية متطلبات لا يقيسها.
5. الاعتماد `INTERNALLY_CERTIFIED / SOURCE_VERIFIED` داخلي فقط، وليس اعتمادًا رسميًا من جهة خارجية.

## 13. حالات التغطية والأدلة والاعتماد والفشل

### 13.1 حالات المهمة الداخلية

`PENDING → READY → RUNNING → SUCCEEDED`، وقد تصبح `FAILED_RETRYABLE`, `FAILED_FINAL`, `BLOCKED_SOURCE`, `BLOCKED_MATH`, `BLOCKED_RIGHTS`, `BLOCKED_EVIDENCE`, `INVALIDATED_BY_CHANGE`.

- فشل اتصال مؤقت: محاولات محدودة مع backoff ثم BLOCKED واضح.
- نفاد وقت/موارد GitHub Actions: checkpoint واستئناف idempotent لنفس مدخلات المهمة؛ لا ادعاء استمرار محادثة ChatGPT آليًا.
- تضارب إصلاحات: كاتب واحد للمكوّن المشترك، ثم إعادة اختبار التأثر.
- شك أكاديمي أو رياضي أو حق غير محسوم: لا إصلاح متهور ولا PASS؛ يستمر العمل المستقل لكن لا تُغلق الدفعة.
- إصلاح مكون مشترك بعد دفعة منشورة: أثره يُراجع على الدفعات السابقة؛ أدلتها المتأثرة تُبطل ويُختبر نطاقها قبل السماح بإصدار جديد.

### 13.2 حالات الدفعة ومتى تتحقق

| الحالة | المعنى الدقيق | تسمح ببدء الدفعة التالية؟ |
|---|---|---|
| `BATCH_REVIEW_IN_PROGRESS` | المراجعة أو الإصلاح جارٍ | **لا** |
| `BATCH_COVERAGE_COMPLETE` | تم تسجيل مقارنة وتحليل لكل الـ500، حتى لو بها أخطاء أو نقص | **لا** |
| `BATCH_NO_GO` | عيب إلزامي أو دليل ناقص أو حقوق مجهولة أو CI/نشر فاشل يمنع القبول/الانتقال | **لا** |
| `BATCH_EVIDENCE_READY` | جميع L1–L6 والأبعاد الثمانية مدعومة بأدلة صالحة على SHA مستقر، 0 عيوب مفتوحة | **لا** |
| `BATCH_CERTIFIED` | بوابة الاعتماد الجماعي اجتازت الأدلة وCI وأصدرت قرار اعتماد داخلي واحد | **لا** |
| `BATCH_PASS_AND_LIVE` | PR الإصدار المعتمد دُمج، Render Live طابق SHA، ونجحت الصحة والتحققات اللاحقة للنشر | **نعم، وفقط هذه الحالة** |
| `PROGRAMME_PASS` | كل الدفعات الأربع `BATCH_PASS_AND_LIVE` و1,560/1,560 | انتهى البرنامج |

`BATCH_COVERAGE_COMPLETE` لا تساوي `BATCH_EVIDENCE_READY`، و`BATCH_CERTIFIED` **لا تساوي** `BATCH_PASS_AND_LIVE`.

يُحفظ `checkpoint` على GitHub يشمل `batchId`, `manifestSha`, `sourceVersion`, `candidateSha`, `taskState`, `evidenceLinks`, `openDefects`, `blockedReasons`, `attempts`, `lastSuccessfulStep`, `resumeCursor`, `publishStatus`، مع ربط آخر head. لا نعِد تشغيل السليم غير المتأثر، ولا نكتب 500 PASS افتراضيًا.
